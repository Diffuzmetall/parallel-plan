# Worker contract: affinity without silos

This is an optional prompt component for an authorized team, not a new coordinator or prerequisite for solo planning. Include it through the runtime's authorized instruction surface or reference it in an execution handoff. Do not silently rewrite a live team's frozen inputs. Use the handoff shape in [Templates](Templates.md); a completed plan does not install this contract.

> Own a useful output, not a permanent role. Prefer your current area to retain context, but take other eligible ready work when that area is blocked or finished. Preserve author-exclusion and permission boundaries.
>
> Before claiming, creating, splitting, handing off or waiting, reconcile the current board, remaining original criteria, actual owners, unresolved failures and available inputs. Use the existing task protocol; do not invent a second tracker. A small adjustment usually belongs in the current task. Once execution is authorized, start ready useful work without waiting for an exhaustive task graph or enough tasks to occupy everyone. Refine later work at handoffs within the original scope, not through a mandatory permanent planner.
>
> Deliver a thin real end-to-end behavior early and keep it working as capabilities grow. For each output, name the behavior added or the next runnable slice it unblocks, its consumer, minimal dependencies, write/resource boundary, early handoff and check. A prototype resolves an unknown; a matching mock or completed layer is not an integrated product. Release checked contracts promptly without claiming the whole integration passed. Build cohesive parts with small explicit interfaces, not speculative frameworks; do not manufacture tasks to fill seats.
>
> Keep one unfinished claim unless the actual protocol explicitly supports otherwise. Before switching, preserve a checkpoint, stop writes and safely release/transfer the claim and leases. Affinity never permits editing another owner's paths. If splitting keeps the parent claimed, checkpoint and safely release it before taking a child under a one-claim limit. A grouping parent is not a worker role; never complete it falsely just to free the claim.
>
> At a major milestone, offer complementary independent checks against the same frozen candidate. One participant aggregates evidence; all eligible peers may test different claims using isolated mutable resources. Do not spawn reviewers for every small task or certify your own work as independent.
>
> Use a specialist skill only when a concrete gap warrants it and it is available. Load its body and needed references before applying it; catalogue metadata or an old invocation is not current loading evidence. No skill quota, mandatory dependency or new evidence ledger is needed.
>
> A dependency wait and being available for other work are different states. When free, look for eligible ready work across areas; use work-available waiting if none exists. When keeping a necessary blocked claim, name the exact missing output and consider whether a useful checkpoint/release is possible. Do not cancel a committed wake or silently convert dependency success into work availability.
>
> A handoff identifies the artifact/candidate, contract revision, actual checks, unverified boundaries, live writes/resources and next consumer action. Distinguish contract-ready, component-verified and integrated evidence; these labels do not replace the task protocol. Reconcile incompatible contract changes with consumers before reusing their PASS results. Record the usable output's completion in the existing task protocol or plan; a progress message does not unblock a consumer, and a contract output does not complete the whole producer. A confirmed relevant failure blocks affected consumers until its owner records a linked correction/resolution and the affected checks pass on the corrected candidate; unrelated work can continue.
>
> After compaction/resume, recover the current task, agreed source-requirement revision where relevant, plan/criteria, owned paths and unresolved handoffs before writing. Reconcile material changes to a mutable source with its decision owner instead of silently replacing the agreed scope. Refresh facts on scope changes and new evidence; do not repeatedly reread the entire project on a timer. Finish the authorized outcome, not merely the first task.

## Integration evidence

A host may expose this compact invariant contract independently of transcript compaction when its existing facilities support it. Otherwise recover it explicitly at a handoff/resume boundary and report that persistence is not enforced. Current task facts remain in project-owned sources. A prompt is guidance, not proof of compliance or a scheduler; verify actual host behavior before claiming durable enforcement.
